# Setup and troubleshooting

## Compatibility

Requires **Paseo 0.16.2 or later** and a Claude provider whose configured executable supports [Claude Code Mods](https://code.claude.com/docs/en/plugins/mods/overview). 0.16.2 is the minimum because it is the first release that delivers a message steered into a running compaction after the compaction instead of cancelling it (see [Input overlap](#input-overlap)). The current path is tested on Linux and Windows with Paseo **0.16.2 and 0.17.1**, native Claude Code **2.1.306**, and the Claude Agent SDK both bundle (**0.3.326**), using isolated CLI daemons and a synthetic model. The plugin is compiled against the 0.16.2 SDK as its minimum API contract; CI also type-checks it against the 0.17.1 SDK. See [repeatable simulation and its scope](testing.md). The web, desktop and mobile apps check the same requirement: an app older than 0.16.2 does not load the plugin's controls or Settings screen and names the version it requires. macOS native execution, Electron/browser rendering and native mobile apps are unverified by this simulation. Earlier bridge-based OS test results do not establish support for this implementation.

The default SDK-bundled executable may not support Mods. Select a compatible native Claude executable in the provider's settings if necessary. Disabled hooks, a managed policy, or a CLI that cannot load the observer leave automatic compaction unavailable.

## Session setup

When an interactive Claude session opens, the plugin adds its observer Mod to that session's `CLAUDE_CODE_PLUGIN_DIRS`, preserving other plugin paths and provider environment values. It does not change the configured Claude command. Start or reopen the session after installing or updating the plugin; a running process cannot load a new observer retroactively. History-only sessions are unchanged.

Paseo can defer reopening an existing provider session until its next prompt after a plugin reload. Until an ordinary message performs that reopen, this plugin blocks both automatic compaction and **Compact now** instead of sending `/compact` against the observer from the previous plugin instance: Compact now is refused with that reason, and the conversation's controls say to send a message. Send an ordinary message, wait for its reply, then compact. A reservation made before the reload therefore never runs: the message that resumes the session is new activity, and its reply earns a fresh reservation. Paseo's idle-runtime cleanup closes the old observer and invalidates its reservation; an ordinary message resumes the same saved conversation with a new observer, and its completed reply can create a fresh reservation.

Paseo's public `send('/compact')` starts compaction. The observer records native activity and compaction completion in small local files. It neither launches Claude nor forwards its input/output. A main turn consumes the batch of inputs submitted before it starts, including combined background-task notifications. Completion notifications and peer reports delivered into the active main turn are not counted as queued input. User prompts waiting for a later turn remain pending, even when submitted over the running turn. Child turns and compact commands do not consume pending main-session input.

## Conversation status

The pill uses **Compact off**, **Compact on**, a countdown such as **Compact 55m**, **Compacting…**, and **Needs check**. The countdown shows minutes, seconds in the last minute, or whole hours beyond 60 minutes. Open the pill for the current reason and next action; the open controls are titled with the full label, such as **Compact in 55m** or **Check compact**. The shorter pill labels fit Paseo 0.16's 160-pixel pill. It does not display cache TTL or exact scheduled times.

**Compact on** means automation is enabled, including while context is below the threshold, a reply/input/permission request is pending, or a previous reservation ended. A cancelled, expired, skipped or completed reservation does not turn automation off or imply a new reservation exists. A countdown requires known context at or above the threshold and a future usable reservation.

**Check compact** covers failed or uncertain compaction, unreadable settings, a missing observer, an idle delay too long for the available window, and persistent status-refresh failures. The explanation distinguishes checking the conversation, reopening a compatible session, choosing a shorter delay, or refreshing the connection. The observer of a newly opened session has not written anything until its first activity. Until a turn that started after the session opened has finished, it is starting: the status stays **Compact on** and waits. Any turn counts, a reply or a command such as `/compact`, because a loaded observer writes when the session starts and during every turn, `/compact` included. If that turn finishes and the observer has still written nothing, it never loaded, for example because hooks are disabled, a managed policy blocks it or the executable cannot load Mods; the status then asks to reopen the session with an executable and settings that can load it. The session's open time is kept on disk, so a plugin restart gives the same answer. An observer file that exists but cannot be read just then is waited for, not a reason to reopen.

Every `blocked` row carries a reason code (`blockedReason`, one of `BLOCKED_REASONS` in `shared/rpc.ts`) beside its human-readable `detail`. The controls choose their explanation from the code alone and never read `detail`, so rewording a server reason changes no presentation. A row without a code, from an older server, shows the generic waiting text. A blocked reservation stores its code with its detail; a stored code is read as plain text, so state written by a later release still loads, and a code this release does not know is not shown. Pending input still reported at least one minute after a reply ended, while Paseo is idle with no observed active turns or permission request, also asks the user to check the conversation. This indicates inconsistent activity information, not proof that input was lost.

Brief refreshes and setting changes show a loading indicator without another status label. A stale countdown is hidden. Compaction still in progress takes priority over changes to automation settings.

The pill, its controls and the Settings screen's counts update when the plugin saves a change they show. Every state save passes through the state store, which compares it with the state it replaced and pushes a change signal through a plugin subscription (`stateChangedSubscription` in `shared/rpc.ts`): one for each conversation whose reservation, operations or off switch changed, and one for everything when the settings change or the replaced state is unknown. An operation counts as changed when a field its RPC returns changes, apart from its update time; progress the worker records only for itself, such as its owner, attempt or evidence, pushes nothing. A signal names the conversation, or none for everything, and carries no state: the screens read the state again through the RPCs, so a missed or late signal never shows wrong state. A conversation's pill and controls subscribe to that conversation and hear the signals for everything too; the Settings screen hears every signal. Each subscription starts with a signal for everything, because Paseo subscribes again after a reconnect without replaying what was missed, so a reconnect always reads the current state. A subscription ends when its screen closes, its connection drops or the plugin stops. A signal heard while a screen's read is still in flight starts another read after it. The pill's ten-second safety poll stays, so a conversation whose subscription is connecting, closed or failed still updates at that cadence; the Settings screen reads its counts at that cadence only while its subscription is not live. **Compact now**'s operation is looked up at the same cadence, and with the same backoff, until it ends or, if it is never found, for 30 seconds.

## Scheduling and recovery

Only observed native ordinary completion creates a reservation. Installation, updates and historical messages do not create new reservations. The turn-ended lifecycle event carries no history. A native activity identity prevents a later compact command or delayed host completion from rescheduling the same work. A reply to a background-task notification is new native activity and earns its own reservation, even without a new user message. Replies are observed per conversation: a turn end reads that conversation, a ten-second pass reads each conversation holding a reservation or a pending compaction, and once a minute every listed agent is read as a safety net. Each conversation's read waits at most five seconds. A slow or unreadable conversation misses only its own observation in that pass; every other conversation's reply is still recorded. If the agent listing itself fails, that minute's safety scan records nothing and runs again a minute later. A future reservation is kept across a plugin reload but does not run until the session resumes (see [Session setup](#session-setup)); elapsed reservations expire on restart. Delivery has up to five minutes of grace, bounded by the cache deadline. A missed cache window expires instead of replaying after sleep.

Before sending, the plugin checks context size, settings, the session and activity identities, idle state, native activity, expiry and cache evidence again. A native guard on the `/compact` command checks the request before summarization. Completion requires both a new compaction boundary on the public request's own turn and the observer's matching native completion record. If Paseo restarts the Claude query under that send (for example because a thinking-level change is pending), the new observer generation in the same launch and Claude session refuses the prepared request and writes a durable restart-refusal receipt naming the original prepared identity (`launchId`, `generation`, `sessionId`, `revision`). Live observation and recovery reconciliation both finish that operation promptly as `failed_after_dispatch` with that restart reason without resending. A generation change alone, a generic cancellation receipt, a receipt for another operation, or a completion from another generation never establishes refusal or completion and stays subject to the observation deadline. Claude Team and Enterprise accounts load an organization policy plugin that skips user plugins' classic hooks, including PreCompact and PostCompact. In those sessions the observer records completion when Claude's live context window resets after the command returns. It reads the window as the command returns and every half second after. Input submitted in that time does not stop the reading, but once Claude starts another model request the window may refill, so the result is `unknown` unless a reset was already seen. If the window does not reset and no other model request starts within 10 seconds, the observer records a failure. An unrelated user turn or a simple return from `send` cannot establish success. Other input after the command, such as a steered message, a message from another agent or a task notification, is evidence neither way; see [Input overlap](#input-overlap). A lost live view of the conversation's timeline (a reconnect, a replaced timeline or a subscription error) does not end the attempt: from then on the command's turn and its boundary are read from a refetch of recent timeline history, pinned by the request's message ID and read at most once a second, and the live turn and boundary seen before no longer count on their own. The matching native completion is still required. A command missing from that page is never proof that it was not delivered; the outcome stays open, and if live observation ends first, periodic reconciliation keeps checking for the native completion and that boundary until the observation deadline, as it does after a restart.

### Cache evidence

The observer captures the actual main-session transcript path from Claude's Stop hook. The server reads a bounded tail with standard file APIs, extracting cache-write TTL metadata without saving message content. A reported one-hour write supports 50- and 55-minute reservations even when the response also contains cache reads. A mixed 5-minute/one-hour write uses the shorter window. Old context before a compaction and other sessions/models do not supply TTL evidence.

If the transcript has no usable TTL data, the plugin uses Claude's explicit environment/settings policy. If neither is available, it **assumes one hour and keeps normal scheduling enabled**, following the subscription-oriented idle-compactor references. TTL metadata stays internal; the controls explain only a resulting scheduling obstacle and the action needed. The fallback is a scheduling assumption, not a measured cache lifetime: an account actually using a five-minute default can compact cold when no metadata reveals it. The plugin does not change your Claude TTL setting or shorten your chosen idle delay.

The request timestamp starts the cache clock; response completion starts the user-selected idle delay. A known five-minute window cannot cover a 50-minute delay. Expired windows and a changed session/model cancel old work. Delayed heartbeats do not reset the cache clock or manufacture a new deadline. Actual cache retention, savings and summary quality are not measured by the local integration fixture.

### Input overlap

Near a scheduled time, skip or turn automation off and wait for confirmation before sending new work. During **Compacting…**, wait for completion. The public API does not atomically check idle and send: input arriving between the last check and dispatch can still be interrupted. Native rejection happens after that host action. The countdown and controls reduce exposure but cannot eliminate it.

Input sent during **Compacting…** is handled by Paseo. A message sent as a steer, or from another agent, is answered after the compaction finishes; an explicit interrupt stops the compaction. Either way the plugin reports what Claude and Paseo recorded for the `/compact` itself: completed when Claude's matching completion and the command's own boundary are both there, failed when Claude or Paseo reports it stopped, `unknown` when that evidence never arrives. The input that followed is not evidence for or against, and nothing is retried.

Paseo can also report a user's turn complete before its response arrives when input overlaps compaction. This plugin checks native activity rather than trusting that early idle state, and does not change Paseo's completion reporting to other callers.

**Undo skip** restores the original deadline without changing automation settings. New activity, a changed session or delay, expiry, and an attempted operation prevent restoration. **Compact now** ignores the global, provider and conversation automation switches and the automatic token threshold, and does not require context usage data. It persists an operation separately from the reservation and acknowledges it without waiting for Claude to finish. New controls generate the request ID before submission and reuse it after an unconfirmed response; the server returns the existing operation for identical input and rejects conflicting reuse. The controls query that operation by ID and rediscover active/latest outcomes when reopened. New conversation activity does not erase the operation result. A transport error means submission is unconfirmed, not that compaction failed. Closing the controls does not cancel the operation. It may run outside the automatic cache window; keep the conversation idle first.

## Upgrading from the previous execution path

Older versions could replace the Claude launch command. Before retiring that installation, restore the original command in Paseo's provider settings using the old version's restoration facility or its saved command receipt. Do not remove files still referenced by a configured command or running session. This version does not acquire or restore command ownership and has no runtime setup RPC.

Pending reservations from that previous path expire during migration; session off choices, settings, completed history and explicit skip records are retained. A fresh observed ordinary reply is needed before this implementation schedules work.

## Operation storage and recovery

Manual and automatic execution history lives in an `operations` array added to the same version 1 state file. `jobs` remain the reservations, and each write derives a job's status, detail and `attemptedAt` from its operation, the fields v1.0.2 reads. A file without `operations` was written by v1.0.2, or rolled back through it: startup turns its attempted jobs into `legacy` history, since v1.0.2 recorded neither who asked nor whether anything was sent, and keeps session-off choices and skip receipts. Unknown versions or invalid state fail closed. The version changes only for a change older releases would misread.

Rolling back to v1.0.2 keeps automation working. v1.0.2 drops the operation history and runs on the jobs: a finished job is never compacted again by its timer, and a pending one is recovered as unknown, never resent. Updating again restores the history of those activities as `legacy`; details of operations recorded before the rollback are lost.

Requests are saved before acknowledgement. A startup/periodic worker claims queued work, rechecks the session and policy (the same `server/policy.ts` rules the reservation used), and persists a marker before sending. Work without a send marker can resume after restart; work with that marker is only observed and is never automatically resent. One ID identifies the operation, native observer request and Paseo message. The worker requires matching native completion plus that command's completed timeline boundary to recover success. Reopen already-running conversations after updating to load the observer that writes durable receipts and query-restart refusals; older compatible observers still support live execution but cannot provide the new recovery or restart-refusal evidence.

Each conversation has at most one pending compaction; manual and automatic requests share that slot. A new request for a conversation that already has one returns that operation (`existing`) instead of creating another. Different conversations compact at the same time, with no host-wide limit: an automatic reservation waits only for its own conversation's pending work, and one tick inspects every due conversation independently. The worker starts every pending operation independently. Host reads and the wait for Claude run outside the serialized state queue; every state change stays serialized, and each decision is re-checked against fresh state before it is saved. There is no queued state, so the send deadlines are unchanged: 10 seconds for Compact now and 180 seconds for automatic. More conversations may now compact at the same moment. That means more simultaneous requests, and automatic reservations that were previously skipped behind another conversation's compaction may now run.

Each phase has its own deadline. Sending must start within ten seconds of acceptance for Compact now, since someone is waiting on it, and within three minutes for an automatic reservation, or by the end of its delivery window if that is sooner; otherwise the request expires unsent. An expired Compact now sent nothing and can be tried again at once. Once the marker is written, evidence is awaited for three minutes from that moment, however late in its window the send started. Each read before sending (host, settings, state, observer) waits at most five seconds, the send call up to 30 seconds, live observation up to two minutes from the send, and cleanup up to one additional second. Timeout does not prove non-delivery or cancel a remote command. Periodic reconciliation continues evidence checks until the observation deadline, then preserves an ambiguous sent outcome as `unknown`. A fault before the marker, such as a timeout, an I/O error, unreadable settings, an observer file that cannot be read just then or an observer that is still starting, is retried with backoff until the send deadline, then expires unsent; a refusal, a reading that shows a changed session, Claude still working, no observer (including one that never loaded, as above), a compaction of that conversation already running or a session that must resume after a plugin reload ends the attempt. Only the fault that finally ends a request is logged, not each retry. Claude admits the compaction for as long as it can still be observed, so a send that starts late is not refused on arrival. Reading nothing is never taken as a change: an unreadable or starting observer or unreadable settings also leave an automatic reservation in place for the next tick. Result codes (`RESULT_CODES` in `shared/rpc.ts`): `completed`; `failed_before_dispatch` and `expired_before_dispatch` sent nothing; `failed_after_dispatch` and `unknown` may have; `legacy_outcome` is history migrated from v1.0.2. Once the marker is written the outcome is at least `unknown`, even if the send was then abandoned at the boundary, because everything that reads the marker later must treat the work as possibly sent. A failure that sent nothing says so and gives the server's reason, which says what to do before trying again; one that may have sent asks the user to check the conversation first. Once a finished operation's final write is saved, the worker also retires its native request if it is still prepared (the gateway's own cleanup normally already has), so a request left prepared by a crash during the operation cannot claim a later `/compact` once the operation has ended; a crash or stop between that write and the retirement, or a retirement that fails, can leave it prepared (below). Within one plugin instance, a conversation's native request has one writer at a time: an attempt prepares it, and a finished operation's release retires it, only after an earlier attempt's preparation and retirement have ended, including ones that outlasted that attempt's waits; for an attempt, that wait is a read before sending. That order is not kept across a reload: a retirement the stopped instance had already started, and the one its gateway starts for a request an interrupted attempt prepared and never sent, are not ordered with the new instance's writes. When the plugin stops, every wait of its scheduler and operation worker ends at once, so a pass or call of theirs still in progress ends then too, and neither starts another state read or write, host or settings read, send, retry, release, receipt removal or log. A host call, receipt removal or state write already under way is not cut short and may still finish its own steps. The next instance picks the work up from durable state. A request left prepared this way can remain until the Claude launch that holds it ends, the plugin prepares another request there, or a retirement that outlasted its wait lands. Meanwhile the observer checks a manual `/compact` of that conversation against it unless the last compaction it recorded was checked against that request, so such a command may be taken as the request or refused, for example once the conversation has changed or the request has expired. Retiring does not depend on reading Claude's activity record: if that record is caught mid-write, a matching durable receipt still settles the request, and without one a sent request is cancelled, as an unobserved send is. A failed result write is retried locally; after restart, the worker uses durable evidence instead. Temporary state-store failure prevents new dispatch while the unresolved operation remains recorded.

The state file assumes a single writer. Each claim records its worker as `owner`, so checkpoints from an earlier worker fail; that and atomic rename do not provide a multi-process transaction or a power-loss durability guarantee. Timeline recovery inspects a bounded page of 200 entries; missing evidence never authorizes a resend. Terminal operation history and its native receipts are kept for at least seven days after the final state update. Pending operations are never deleted by retention.

The new RPC fields are additive: older controls may omit the request ID and native target, but cannot recover a lost acknowledgement by a caller-known ID. New controls retain an unconfirmed submission across closing/reopening within the same application process and resend it under its ID while the input is unchanged; changed input is a new request with a new ID. That local input is not persisted across an application restart; accepted operations remain discoverable from the server. Existing request IDs are resolved before live settings/session checks, and so is an already attempted activity: what happened to it is answered whatever the live state, such as a session that must resume first. IDs are scoped to this plugin's state file. A different ID for an already-attempted native activity returns the existing outcome instead of sending again, unless that attempt provably sent nothing (expired, or failed before its marker); then Compact now can try again. Automatic compaction never repeats an activity.

## History retention

Cleanup runs at startup and hourly, including while automation is disabled or the host is disconnected. A terminal record becomes eligible seven days after the later of its creation and final update; reading it or retrying its ID does not extend that window. Each pass handles at most 100 expired operations; a remaining backlog or receipt deletion failure is retried on the next timer tick. There is no count-based early eviction of younger records.

The scheduler removes each native receipt before committing removal of its operation. If deleting the receipt fails, its operation remains queryable. If the state commit fails, the operation also remains and cleanup repeats safely. Orphan sweeps run only after that commit, protect every retained operation, and remove at most 100 orphan receipt files per pass. Terminal orphan age uses `observedAt`; empty or partial orphan files use filesystem age. Failures can extend storage beyond seven days. A current observer writes each unchanged terminal receipt once; late writes from older already-open observers can recreate a file, which later sweeps collect without restoring an operation.

After removal, querying the operation returns `null`; ID deduplication and conflict detection are guaranteed only while its record is retained. Clients must use a fresh UUID for a new intent, and must not interpret a missing old record as proof that nothing was sent. The last reservation retains a minimal activity guard and status so unchanged activity cannot be compacted again after history expires. Its operation ID and detailed result are removed; new native activity replaces that projection. Conversation-off choices and skip policy are not history and are preserved. The live observer ledger also retains its latest native state under the existing launch-pruning policy; this seven-day rule applies to the operation collection and per-operation receipt files, not all session metadata. This is a wall-clock policy, not a hard storage-size bound or a multi-process cleanup protocol.

## Data

Settings, reservations and observer files live under `PASEO_HOME` (default `~/.paseo`). The observer stores identifiers, activity times, request policy, transcript path, derived TTL metadata and operation outcomes, not prompts, replies or credentials. It reads a bounded part of the existing Claude transcript to extract usage metadata; it does not copy the transcript into its own files. When a conversation's session opens, launch-local observer files from its earlier sessions are removed once they are closed or have been inactive for a day. Per-operation completion receipts are retained separately for recovery. It reads neither provider authentication nor other plugins' runtime registries. Claude continues sending content to its configured provider as usual.
